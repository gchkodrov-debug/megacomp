## 1. ROUTE DECISION — how the cartoon is drawn and run

**Chosen: a hand-drawn SVG vector rig, posed procedurally every frame** (`solnik-toon.js`, one builder function draws the character; a `Toon` class computes every joint/face/mouth transform per frame). No image assets, no model files, no raster frames.

Alternatives weighed:
- **Frame-sequence sprites (raster):** would need hundreds of generated frames for 11 clips × expressions × visemes; per-frame consistency across generated images is the known failure mode of the image lanes; file weight blows the budget; speech-sync is frame-index bookkeeping. REJECTED on consistency + weight evidence.
- **Rive/Lottie:** excellent cartoon feel, but the .riv/.json would have to be authored in external editors we don't have in the stack, state machines for 15 visemes + 10 expressions + locomotion blending are hard to verify headlessly, and the runtime adds weight. REJECTED on authoring/verifiability evidence in this stack.
- **SVG rig (chosen):** identity is STRUCTURAL — one builder draws every view/expression/clip, so the face cannot drift between frames (the make-or-break requirement). Weight: rig 18.6 KB + engine 53.6 KB ≈ **72 KB total, vs ~5.4 MB for the 3D stack it replaces** (48.5 KB JS + 1.58 MB GLBs + 3.4 MB three.js/vendor + VAD). 60 fps transforms on compositor-friendly properties; zero layout impact (fixed overlay, CLS-safe by construction — the stage is out of flow). Speech sync: mouth shapes are data (a 17-shape path table), driven by the same analyser bands as the proven build.

**Character sheet (deliverable 1):** `cartoon/character-sheet.html` + `cartoon/shots/sheet-full.png` — front / three-quarter / side views, all 10 expressions, all 15 visemes + smile/grin, 11 clip poses, and the 6 environment-interaction poses — every cell rendered by the SAME builder, which is the consistency proof. Identity vs the canonical portrait (`solnik-character-v1.jpg`): brass dome head with engraved swirl band + side ear caps, HUGE amber eyes (enlarged after the first sheet review), small curved smile, segmented neck, bronze bell torso, faceted golden crystal heart with glow, segmented arms with 3-finger hands + trailing ribbon cables, jointed legs with claw feet. Town palette throughout (#141210 / #C9A227 / #6B5626 / #E9DDC6).

## 6. ENVIRONMENT INTERACTION (the addendum — how each of the four is satisfied)

Page-side contract (what universe pages/engine specimens emit; mirrors `universes.js`):
- Anchors: `[data-solnik-anchor]` elements may add `data-solnik-kind="perch|portal|instrument|object"`, `data-solnik-verb="emerge|operate|inspect|read|open|touch|point"`, `data-solnik-label="…"`, `data-solnik-target="<css selector>"`, `data-solnik-depth="behind"`, and the existing `data-solnik-x`.
- Foreground: `[data-solnik-occluder]` on machinery/environment elements.
- Events (document): `solnik:arrive {anchorId, kind}` on every landing; `solnik:interact {anchorId, verb, label, target}` when an interaction gesture plays — the page syncs its real elements (press cycles, astrolabe turns, ledger opens) to these.
- API: `__solnik.interact(anchorId)`, `__solnik.enterPortal(anchorId) → Promise<boolean>`, `__solnik.emerge(anchorId)`.

1. **Occlusion (walking BEHIND machinery):** the stage is a body-level sibling of the sovereignty root and lives on two z-planes — front `2147482999`, behind `3`; the module raises `[data-solnik-occluder]` elements to z-index 6 (position preserved/raised only when static/auto), so on the behind plane the machinery genuinely covers him. Plane is computed live: behind while perched on a `depth="behind"` anchor, or while his body's box crosses an occluder's box mid-route; a brightness/saturation depth cue (0.87/0.94) rides the behind plane. The sovereignty pill + caption NEVER sink (separate root at 2147483000). PROVEN: probe-toon6 W3/W3b/W3c + `world-behind.png` (only his head clears the press — real occlusion, not a fade).
2. **Portals:** when a page offers a `kind="portal"` anchor, his entrance IS an emergence — he grows out of the portal's golden glow at that anchor (`enteredVia: 'portal'`, loco mode `emerge`, rig portal-glow ellipse + scale-in). `enterPortal()` walks him to the gate and takes him through (shrink into the glow → gone; the promise resolves when he's through — the engine navigates on resolve); `emerge()` brings him back through. Brain `guide` to a portal plays the emerge gesture + fires the interact event (navigation remains the page's, per the engine's portal hrefs). PROVEN: probe-toon6 W1/W4/W4b + probe-toon7.
3. **Approaching instruments:** `kind="instrument"` anchors are first-class destinations for every driver (scroll-follow, Summon, brain guide, `__solnik.interact()`); he routes there on legs (walk/run/climb/drop), lands, and turns to FACE the instrument element itself (`interact.target` centre), not the anchor's facing. PROVEN: probe-toon6 W2 (approach + arrival state at `mint-press`).
4. **Object interaction (touch/point/operate, page-synced):** on arrival at any verb-carrying anchor he performs the verb's gesture — `operate` (two press cycles, body lean), `touch`/`open` (reach + tap), `inspect`/`read` (lean-in + point + head-down), `point`, `emerge` (greet) — and dispatches `solnik:interact` with the verb/label/target so the page can sync the real element in the same beat. An engagement window keeps voluntary locomotion from dragging him off mid-interaction (brain orders and sovereignty always outrank it). PROVEN: probe-toon6 W2/W2b/W3d/W5 (operate + inspect gestures observed live; event payload verb/target/label exact).

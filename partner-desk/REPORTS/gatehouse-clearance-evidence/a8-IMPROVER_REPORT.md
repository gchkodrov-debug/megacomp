## 3. Fixes made in scope (each with its test)

**FIX-1 — garbage blockhash refused at challenge issuance** (`gatehouse.mjs`, challenge door). The builder validated only string length (32–44 chars): a non-base58 or wrong-length stamp could be reserved, producing a reservation no transaction could ever claim against. Now the blockhash must base58-decode to exactly 32 bytes (400 otherwise). *Test: R19 first leg.*

**FIX-2 — the invented-stamp squat (finding F-01, the leg's main catch).** Challenge stamps are caller-declared and the builder's server trusted them completely: a valid payer proof could stamp `lastValidBlockHeight` = observed + 10,000,000 (or any far-future value) with an invented blockhash. The bound claim could then never match, and the evidence release could never fire — the single anchor lock would be bricked until manual state-file surgery. The lying stamp was *not* self-defeating in any acceptable sense: it converts a recoverable expiry into a permanent lockout, and the realistic trigger is not malice but accident (wrong-cluster stamp, stale client, a blockhash fetched from a different source than the gate's chain). Fix: the reserve door now observes `getBlockHeight` through its own `forward()` **before** the synchronous check-and-persist and refuses (400) any stamp whose `lastValidBlockHeight` sits outside ±1000 heights of the server-observed height (an honest fresh stamp sits ≈ +150; the window also refuses cross-cluster stamps, whose heights differ by millions). Observation unavailable → 502, nothing reserved (fail closed, the release door's Defect-02 discipline). Reserve atomicity is unchanged: the await precedes the sync section, so racing reserves still serialise on `reserveAnchorLock` — proven by R21 (same-tick race) and R6/R6+ re-runs. *Tests: R19 (squat + cross-cluster refused despite valid payer proof, honest stamp reserves), R21, full-suite re-runs.*

**FIX-3 — release door re-reads disk after its await.** The post-observation re-check rested on in-memory state alone; it now calls `refreshAnchorRecordFromDisk()` first (the claim path's critic-N6 discipline) and refuses 503 if the store broke in the interval. No behaviour change in the single-process deployment; it removes a stale-memory assumption after an await. *Covered by R15/R22/R23 re-runs.*

## 4. Builder's NEEDS-CHECK items N1–N6 — adjudicated

- **N1 — challenge burns on failed proof: CONFIRMED, keep.** Consume-on-any-attempt is the correct anti-oracle posture: a failed proof that left the challenge alive would let an attacker iterate signature guesses against a fixed canonical message, and would let one challenge be probed against both doors repeatedly. The cost (an honest buggy client fetches a fresh challenge per attempt) is one extra round-trip on a door that is already two round-trips. R12 (replay) and R20 (cross-purpose burn) pin the behaviour.
- **N2 — twin network paragraph: CONFIRMED.** Full diff of twin vs main page shows only the claimed deltas (title, rehearsal banner, network paragraph, meta line, `CLUSTER='devnet'`, RPC base + route comment, wallet line, Solscan `?cluster=devnet`, twin-local mirror key). The paragraph now reads: *"Solana DEVNET — rehearsal cluster only: devnet SOL has no value, and a signed rehearsal anchor proves the flow, never the day. It is not mainnet."* — accurate, unambiguous, no mainnet claim anywhere in the twin.
- **N3 — claim-409 bodies in the reservation era: CONFIRMED sufficient for safety; one operability residue carried as NC-2 (§5).** Traced every 409 branch through the page: (i) `conflict` (record CLAIMED-or-later under a different signature) carries `signature` + `status` → `heldSignature` set → the page converges its mirror to the authority and stops — correct; (ii) `no-reservation` / `reservation-mismatch` / `blockhash-mismatch` carry `status` only, and *should*: a RESERVED record has no signature to converge to, and inventing one would be a lie. In those branches the page keeps its own signed mirror (conservative), throws the "do NOT sign again until reconciled" stop, and never broadcasts — verified in code (`driveAttempt` claim catch + `runAttempt` latch) and by R14/R16. The reserve-409 branch separately re-reads `anchor-state` and converges only when the authority names a signature; a RESERVED holder leaves the mirror untouched — correct. The one residue: if a reservation is evidence-released *after* a session persisted a signed mirror for it, that mirror's signature can never be claimed, and the page's reconciliation reads it as `locked` forever (Defect-02 discipline: a null status is never proof of non-landing). The escape is the house's standing manual clear with evidence — safe, but it must be written into the ceremony runbook (NC-2).

## 5. Adversarial findings (two-axis discipline — each was attacked before it was graded)

- **F-01 · Invented-stamp squat — CONFIRMED (was a real weakness), FIXED (FIX-1 + FIX-2), tests R19/R21.** See §3. Before the fix, a far-future stamp + invented blockhash bricked the lock permanently; after it, the worst a lying stamp can do is reserve a real-shaped blockhash inside a ±1000-height window — claimable normally, and evidence-releasable within ≈1000 heights (~7 minutes) even if abandoned.
- **F-02 · Purpose replay (reserve challenge → release door and vice versa) — REJECTED as a vulnerability.** The canonical message binds `action:` + purpose-specific fields, `consumeChallenge` checks purpose, and any attempt burns the challenge. Proven by R20 (both directions 403 "purpose mismatch"; honest reserve unaffected).
- **F-03 · Reserve race at the server — REJECTED.** `reserveAnchorLock` is fully synchronous (disk refresh → lock check → atomic persist, no await between); FIX-2's observation await was placed *before* it, not inside it. R21 fires two reserve POSTs in the same tick with distinct challenges and valid proofs: exactly [200, 409], one record. R6 (real devnet) and R6+ (page race, signTransaction total == 1) re-pass.
- **F-04 · Release abuse — REJECTED.** Unauthenticated/wrong-payer proof → 403 and the record stands; body id ≠ challenge-bound id → 400; release while the stamp is still valid → 409 (R15); release of a CLAIMED record → 409, record stands (R22). Release has exactly one key (payer proof) and one evidence rule (server-observed height past the stamp); RPC null/error → 502, no transition (builder's R15 stub legs + code trace).
- **F-05 · Claim with an EXPIRED_UNCLAIMED reservationId — REJECTED.** `claimBoundReservation` honours only a live RESERVED record; the expired id meets a signature-less EXPIRED record and returns `conflict` 409, record untouched. Proven by R23 leg 1. Expiry frees the lock; it does not resurrect the binding.
- **F-06 · Crash between reserve and sign — REJECTED (wired as designed).** The page persists its mirror only *after* signing, so a post-reserve crash leaves no mirror: on next load the gate's `reserved` action and `driveAttempt`'s state-read both refuse before *any* wallet call — not even a message proof (R13: second session 0 wallet calls of either kind). Recovery is the evidence release once the stamp ages out — by design, and see NC-1.
- **F-07 · Stale-mirror reservationId — REJECTED.** The resume path takes `reservationId` from the **server's** record (`serverRec0.reservationId`), never from the mirror; the mirror supplies only the signature + blockhash, and the claim re-binds all three server-side. R23 leg 2 seeds a mirror carrying a deliberately wrong reservationId: the page completes the bound claim under the server's id with 0 new wallet signatures. A mirror from a different browser simply has no local record at all → F-06's refusal path.
- **F-08 · `anchor-state` exposes the reservationId — REJECTED as a vulnerability.** The id alone authorises nothing: reserve/release need the pinned payer's ed25519 proof, claim needs the payer-signed frozen transaction + blockhash binding. Knowing the id lets a stranger *watch* the ceremony state (status/stamps are equally visible) and fetch challenges that create no lock and no record. The builder's reasoning stands; the exposure is deliberate and documented in `publicAnchorRecord`.
- **F-09 · Send-path bypass of the reservation — REJECTED.** The RPC `sendTransaction` door still runs A7's `claimAnchorLock` (send-claim). Against a RESERVED record it conflicts (signature `null` never equals a real signature; RESERVED is not lock-free), so no send can convert or bypass a reservation; after a bound claim it is the same signature and answers `held`. A send-first claim over a lock-free record requires the payer's actual signature over the frozen bytes — that is A7's designed behaviour, not an A8 hole.
- **F-10 · Challenge-map growth / challenge spam — REJECTED.** Issuance creates no lock and no record (property (b) is structural here), the map is pruned and capped at 1000, and every A8 door is per-IP bucketed. Spam costs the spammer rate budget, nothing else.
